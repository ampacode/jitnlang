# nlang-cpp

C++-реализация компилятора, интерпретатора и рантайма для языка программирования nlang.

## О проекте

nlang — экспериментальный язык программирования со статической типизацией, классами, лямбдами и встроенной стандартной библиотекой. Этот репозиторий содержит C++-версию ядра: лексер, парсер, AST, интерпретатор на NObject, виртуальную машину, JIT-компиляцию, систему модулей и горячую замену кода.

Цель `nlang-cpp` — показать, что один и тот же фронтенд может питать два независимых бэкенда: интерпретацию «здесь и сейчас» и кодогенерацию в C++ со сборкой нативного исполняемого файла. Публичная версия здесь очищена от `nsystem`/Qt-шелла и других внутренних деталей, чтобы показать именно компилятор и рантайм.

## Как это работает: логическое устройство компилятора

### 1. Пайплайн

```
исходный код nlang (.nlc)
        ↓
    лексер (src/lexer.cpp)
        ↓
    поток токенов
        ↓
    парсер (src/parser/*.cpp, рекурсивный спуск)
        ↓
    AST-дерево (Node, src/node.h)
        ↓
    ┌───────────────────────┴───────────────────────┐
    ↓                                               ↓
 eval() — интерпретация                       cpp() — кодогенерация
    ↓                                               ↓
 NObject + VM + JIT                         temp.cpp
                                                ↓
                                          g++ (NLANG_CXX)
                                                ↓
                                             a.exe
```

### 2. Почему это работает

**Единый фронтенд.** Лексер и парсер строят абстрактное синтаксическое дерево (AST). Они не знают, будет программа интерпретироваться или компилироваться. Это позволяет добавлять новые конструкции языка в одном месте.

**Зеркальные бэкенды.** Каждый узел AST реализует два метода:
- `eval(Nvm&)` — исполняет программу на лету;
- `cpp(...)` — генерирует C++-код.

Эти методы не делят состояние, не вызывают друг друга и работают с одним и тем же деревом. Поэтому один и тот же `.nlc`-файл можно запустить в интерпретаторе или превратить в `.exe`, не меняя парсер.

**Объектная модель NObject.** Интерпретатор оперирует единым динамическим типом `NObject`, который может хранить числа, строки, списки, словари, функции и экземпляры классов. Это упрощает `eval()` и делает поведение интерпретатора предсказуемым.

**Виртуальная машина и JIT.** `src/nvm.cpp` исполняет байткодовые представления горячих участков. `src/jit.cpp` и `src/jit_rt.cpp` компилируют частые функции прямо в x64 машинный код, минуя внешний g++. Это даёт близкую к нативной скорость без оверхеда C++-сборки.

**Предкомпилированные модули.** Стандартная библиотека (`math`, `str`, `file`, `json`, `regex`, `crypto`, `internet`, `tcp`, `sys`, `qt`, `gl` и др.) собирается один раз в статическую библиотеку `libnlmodules.a`. Сгенерированный C++-код линкуется с ней, поэтому время сборки пользовательской программы не зависит от размера стандартной библиотеки.

**Реестр модулей.** `src/includedlib/modules.cpp` — единая таблица дескрипторов. Чтобы добавить модуль, нужно:
1. Создать `modules/nlm_<name>.h/.cpp` — реализацию.
2. Создать `src/includedlib/<name>.h` — дескриптор с `ModuleDescriptor`.
3. Добавить одну строку в `modules.cpp`.

Это делает систему модулей открытой и легко расширяемой.

**Горячая замена (hotswap).** `src/hotswap.cpp` позволяет обновлять код во время работы: скомпилированные DLL/сектора можно перезагружать, а интерпретатор продолжает работать с актуальными определениями.

### 3. Структура AST

- `src/expressions/` — узлы AST для выражений: числа, строки, переменные, бинарные операции, вызовы, лямбды, индексация, условные выражения.
- `src/statements/` — узлы AST для инструкций: `if`, `while`, `for`, `foreach`, `return`, `break`, `continue`, `function`, `class`, `model`, `using` и др.
- `src/parser/` — рекурсивный спуск, который из токенов строит эти узлы.
- `src/infer.cpp` — базовый вывод типов и анализ, помогающий `cpp()` генерировать корректный C++.
- `src/opt.cpp` — оптимизации AST, включая распознавание векторных паттернов.

### 4. Рантайм

- `runtime/nlrt.h` — заголовки, которые видит сгенерированный C++-код.
- `src/nobject.cpp` — реализация `NObject`.
- `src/nvm.cpp` — виртуальная машина.
- `src/jit.cpp` / `src/jit_rt.cpp` — JIT-компиляция x64.
- `runtime/hotabi.h` — ABI для горячей замены.

## Сборка

### Требования

- CMake 3.16+
- C++20-совместимый компилятор (проверено на TDM-GCC 10.3 и ucrt64 g++)
- (опционально) Qt6 для модулей `nlm_qt` / `nlm_gl`

### Пошагово

```bash
cd nlang-cpp-show
cmake -S . -B build -G "MinGW Makefiles"
cmake --build build --config Release -j 2
```

Если Qt6 не найдено, Qt-модули просто отключаются автоматически.

### Параметры командной строки

```bash
nlang <file.nlc> [-o out.exe] [-b] [--tokens] [--cpp] [--eval]
```

- `<file.nlc>` — исходный файл nlang.
- `-o out.exe` — имя выходного файла при C++-кодогенерации.
- `-b` — только собрать, не запускать.
- `--tokens` — вывести лексерные токены и выйти.
- `--cpp` — вывести сгенерированный C++-код и выйти.
- `--eval` — **интерпретировать программу, не вызывая g++**.

## Проверка и бенчмарки

### Smoke-test

```bash
build/nlang.exe test/classes.nlc --eval
```

Вывод:

```text
30
none
Vlad
31
0
```

### Режим интерпретатора

Запуск с `--eval` обходит C++-кодогенерацию и g++, выполняя AST напрямую.

| Тест | Среднее время, 10 запусков | Примечание |
|---|---|---|
| `test/classes.nlc` | **~23.8 мс** | парсинг + eval + вывод |
| `test/bench.nlc` | **~61.4 мс** | парсинг + eval + измерения |

### Результат `test/bench.nlc` (интерпретатор)

```text
== nlang bench ==
  arith acc=8.33332e+11
arith(1e6): 5 ms
calls(1e6): 1 ms
fibo(28)=317811: 2 ms
  strcat len=100000
strcat(1e5): 1 ms
  lists acc=499999500000
lists(1e6): 23 ms
hotloop x80(2e4): 1 ms
```

Резюме: даже интерпретатор nlang выполняет миллионы итераций за единицы миллисекунд. Самые тяжёлые операции — работа со списками (`lists(1e6): 23 ms`), что ожидаемо из-за динамических `NObject`.

### C++-бекенд

Если не указывать `--eval`, `nlang` генерирует `test/cppOut/temp.cpp` и вызывает `g++` для сборки нативного `a.exe`. Путь к компилятору:

1. `NLANG_CXX` (env)
2. `C:/msys64/ucrt64/bin/g++.exe`
3. `g++` из `PATH`

Для успешной сборки сгенерированных программ `g++` должен видеть:
- `libnlmodules.a` (копируется рядом с `modules/` при пост-билде);
- `runtime/` с `nlrt.h`;
- системные библиотеки модулей (`bcrypt`, `ws2_32`, `iphpapi` и др.).

`test/bench.nlc` в режиме C++-бекенда не замерен, потому что требует корректно настроенного тулчейна с совместимой `libstdc++` и всеми импортными либами модулей. При правильно настроенном `NLANG_CXX` он будет заметно быстрее интерпретатора.
