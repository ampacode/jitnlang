# Архитектура nlang-cpp

Nlang — язык с двумя путями исполнения одного и того же AST:

```
исходник .nlc
    │
    ▼
Lexer (lexer.cpp) ── поток Token'ов (indent-блоки → синтетические { })
    │
    ▼
NParser (parser/*.cpp) ── список Node (AST)
    │
    ├── eval-путь (интерпретатор): каждый Node::eval(vm) исполняет
    │   программу напрямую над NObject-значениями.
    │
    └── cpp-путь (компилятор): каждый Node::cpp(vm) печатает C++-код
        → temp.cpp → g++ → исполняемый файл.
```

Два пути — **зеркальные методы одного алгоритма** на каждом узле,
а не две разные реализации языка. Это принципиальное требование:
правило вычисления живёт в одном месте логически, хоть и записано дважды.

## Карта каталогов

| Путь | Что | Аналог в python-версии |
|---|---|---|
| `src/type.h` | id токенов, операторы | `type.py` |
| `src/lexer.*` | токенизация + indent-блоки | `lexer.py` |
| `src/nobject.*` | `NObject` — динамическое значение | `nobject.py` |
| `src/nvm.*` | `Nvm` — переменные, типы, скоупы, UFCS | `compiler/nvm/nlcnvm.py` |
| `src/node.h` | базовый `Node` + `Emitted` | общий интерфейс узлов |
| `src/infer.cpp` | вывод типов `inferType` и др. | методы `Nvm` |
| `src/parser/` | `NParser`, разбит по секциям | `parser/nparse.py` |
| `src/expressions/` | узлы-выражения, файл = класс | `compiler/expressions/*.py` |
| `src/statements/` | узлы-операторы, файл = класс | `compiler/statements/*.py` |
| `src/run.cpp` | сборка программы в один .cpp | `run.py` (`get_code`) |
| `src/main.cpp` | CLI-драйвер | `run.py` (`main`) |
| `runtime/nlrt.h` | рантайм сгенерированного кода | C++-куски из includedlib |

## Node — мультитаргетный узел

```cpp
struct Node {
    // кодогенерация по таргетам
    virtual Emitted cpp(Nvm&);
    virtual Emitted javascript(Nvm&);
    virtual Emitted html(Nvm&);
    virtual Emitted css(Nvm&);
    // интерпретатор
    virtual NObject eval(Nvm&);
    // anti-режимы (выполнение на этапе компиляции)
    virtual bool isAnti(Nvm&);
    virtual Emitted anticpp(Nvm&);
    virtual Emitted antijavascript(Nvm&);
    virtual Emitted antihtml(Nvm&);
    virtual Emitted anticss(Nvm&);
    virtual NObject antieval(Nvm&);
};
```

`Emitted` — обёртка над строкой сгенерированного кода
(аналог `CppXxxExpression.getCpp()` из python-версии).

## Горячая замена (задел на будущее)

`NFunction` хранит `std::atomic<NativeFn> impl`. Сейчас `nullptr` →
функция исполняется интерпретатором через `execFunctionBody`.
План: когда регион скомпилирован, указатель подменяется атомарно —
интерпретатор на следующем вызове уже попадает в машинный код.
См. `docs/architecture/tiered-execution.md` (будет написан при реализации).

## Текущий синтаксис (новые правила)

- `;` запрещена — разделитель только перевод строки
  (внутри `for( ; ; )` остаётся).
- `{ }` для блоков запрещены — блоки строятся отступом.
  Реальные `{` остались у лямбд `(a) { ... }`, словарных литералов
  `{ "k": v }` и будущих vc-шаблонов. Indent-блоки помечены
  `Token::synthetic` — парсер различает их и ругается на «ручные» скобки.
- Скобки условий обязательны: `if (x)`, `while (x)`, `for (...)`.
- Индексация с нуля: `a[0]` — первый элемент.

## Инклуды и горячая перезагрузка

`using <file.nlc>` / `using <file.nlb>` — инклуд nlang-исходника.
Путь относителен каталогу входного файла.

- **eval-путь:** файл лексится, парсится и исполняется интерпретатором.
  Функции помечаются `hot_path`/`hot_mtime` (штамм = хэш содержимого —
  `stat` на MinGW даёт закешированное mtime). При каждом вызове, если
  файл изменился, он перезагружается и зовётся свежая версия —
  изменение видно сразу, внутри работающего цикла.
- **cpp-путь:** файл встраивается на этапе компиляции (как `#include`):
  функции/классы — в область объявлений, остальное — инлайн.

Это ступени tiered-модели: «интерпретируется мгновенно → встраивается
при компиляции». Следующая ступень — hot-swap.

## Живой hot-swap (eval -> dll)

В `--eval` включён `vm.hot_swap`: интерпретируемая функция,
вызванная `>= vm.hot_threshold` раз (по умолчанию 200,
`NLANG_HOT_THRESHOLD` для тюнинга), компилируется в dll вживую:

1. `decl->cpp(vm)` — тело функции эмитится как обычный C++.
2. Вокруг генерируется `extern "C" nl_hot_call(NLArg*,n,NLRet*)`
   shim (`runtime/hotabi.h`) — через границу dll идут только POD,
   потому что dll не линкуется к exe и `std::string`/`shared_ptr`
   пересекать границу нельзя.
3. `g++ -O2 -shared` → `%TEMP%/nlhot_<name>.dll` — в ФОНОВОМ
   потоке: вызовы продолжают идти через интерпретатор без паузы.
4. Готовая dll публикуется атомиками (`hot_abi`, `hot_state=2`);
   `call()` проверяет атомики без локов.

**Обратный мост dll -> eval:** dll экспортирует `nl_set_host`,
exe подаёт `nl_host_bridge`. Для каждой интерпретируемой
nlang-функции с POD-сигнатурой в dll генерируется трамполин:
`int helper(int x) { marshal -> g_host("helper",...) -> unmarshal }`.
Так dll может звать eval-функции напрямую по имени.

**Коллекции через ABI:** `vector<T>`/`list<T>`/`JValue`
параметры и результаты идут как JSON-строки (`runtime/nljson.h` —
парсер в header'е, чтобы dll обошлась без libnlmodules).
`NLRet::str` — 64КБ под сериализованный результат.

**Ограничения (осознанные):**
- `auto`, голые `list`/`dict`/`map` (без `vector<T>`/`JValue`)
  не переносятся — функция остаётся интерпретируемой;
- вызовы в функции с неподдержанными сигнатурами или в
  модульные нативы не линкуются — тихий откат (hot_state=-1);
- рекурсия работает: имя функции внутри dll ссылается на её же
  скомпилированную копию;
- dll живут до конца процесса (g_hot_modules).

## vc / nls

`docs/language/vc_nls.md`. vc — компилируется в сборку
`std::string` (или конкатенируется в eval), без DOM и без js.
`view("x")`/`style("x")` — в eval парсятся при каждом вызове
(правки видны сразу), в cpp рендерятся на этапе компиляции.
`.nlb` инклудится как обычный nlang-файл с hot-reload —
js-таргет сознательно не переносится.
