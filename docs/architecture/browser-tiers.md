# Браузерный рантайм: 4 стадии аннигиляции

Как nlang-код ускоряется в браузере от интерпретатора до прямого
wasm-байткода. Демо — `nlang-cpp/wasm/out/index.html`.

## Архитектура

```
.nlc исходник (виден в странице — защита языком, не секрет)
    │
    ▼
nlang.wasm — интерпретатор (emscripten, -fexceptions, 16MB стек)
    │
    ├── стадия 1 · eval — AST-интерпретация через nl_call
    │       каждый вызов: JSON-аргументы -> NObject -> JSON
    │       медленно, но работает всё (списки, классы, строки)
    │
    ├── стадия 2 · jit→js — Node::javascript() -> new Function
    │       nl_fn_js(name) возвращает текст `function f(args){...}`;
    │       обёртка with(Proxy) перехватывает неизвестные имена:
    │       рекурсия — прямая (имя функции видно в её скоупе),
    │       остальные имена -> NL.resolve -> trampoline в wasm.
    │       V8 оптимизирует результат — ~4000x от eval на рекурсии.
    │
    ├── стадия 3 · nlang→wasm — wasmjit.cpp: AST -> wasm-байткод
    │       nl_wasm_module() возвращает base64 модуля со всеми
    │       tintable-функциями (один модуль, exports по именам).
    │       f64-подмножество: арифметика, сравнения, if/else,
    │       while, for, return, локальные переменные, вызовы
    │       между функциями модуля (рекурсия — прямой call).
    │       Всё остальное -> WasmJitUnsupported -> остаётся на
    │       стадии 2/1. Ещё быстрее js (~0.26ms на fib(25)).
    │
    └── стадия 4 · стабилизация — диспетчер закрепляет tier
            per-функция; недетерминированные функции живут на
            своём уровне навсегда.
```

## Диспетчер разогрева (NL.dispatch)

```
call_count(name) <= 3  -> eval      (холодный старт, ноль накладных)
call_count(name) > 3   -> jit→js    (если nl_fn_js не "")
wasm_mod[name] есть    -> wasm      (после buildWasm)
```

Это честное "разогревание": первые вызовы не платят за компиляцию,
горячие — получают максимум.

## Экспорты wasm-модуля интерпретатора

| функция | назначение |
|---|---|
| `nl_run(src)` | прогнать исходник, вернуть stdout+ошибки |
| `nl_reset()` | свежий Nvm между запусками |
| `nl_fn_js(name)` | JS-текст функции или "" |
| `nl_call(name, json)` | вызов по имени, JSON->NObject->JSON |
| `nl_fn_names()` | список tintable-кандидатов |
| `nl_wasm_module()` | base64 wasm-модуля (все tintable fn) |

## Ограничения стадии 3 (подмножество v3)

Типы (per-local): `int`/`bool` → i32, `dbl` → f64,
`str`/`list`/`dict`/`json` → **externref** (JS-объекты
передаются напрямую — ноль копирования, никакой linear
memory на границе wasm↔JS).

Контейнеры через externref + импортируемые env-хелперы:
- списки `[1,2]` → `_arr_new`/`_arr_push`; `a[i]` →
  `_arr_get` (работает и на строках — JS `a[i]`);
  `a[i]=v` → `_arr_set`; `l.push(x)` → `_arr_push`;
  `l.pop()` → `_arr_pop`; `len(l)`/`l.len()` → `_len`
- методы (obj на стеке первым аргументом): `push pop join
  slice split contains has index lower upper replace match
  test len size` — regex через `_match`/`_re_test`
  (JS-RegExp на стороне env)
- `&&`/`||` — честное короткое замыкание через `if (i32)`:
  правый операнд не вычисляется когда не нужен (как в eval)
- dict `{k:v}` → `_obj_new`/`_obj_set`; `a.b` → `_obj_get`
  (ключ-идентификатор = строковый литерал);
  `a.b = v` → `_obj_set`
- `foreach` `for v : xs` → desugar: контейнер+индекс как
  скрытые локали (`__fe_a*`, `__fe_i*`), `key` = индекс i32
- boxing: любое значение → externref (`_box_i/_box_f`),
  обратно — `_unbox_i/_unbox_f`, `int(x)`/`dbl(x)` на
  externref → `_int`/`_dbl`
- truthiness: `if (obj)` → `_truthy` (JS truthy-семантика),
  `if (f64)` → `!= 0.0`, `if (i32)` → как есть

Строки: литералы → импортируемые `global externref`
(`nl_wasm_literals` отдаёт JS список); операции через
env-хелперы: `_cat` (s+s), `_seq` (==/!=),
`_print_e/_print_i/_print_f`, `_str_i/_str_f` (str()),
`_len` (len()). Конкатенация число+строка автоматически
приводит через `_str_*`.

Числа: i32-арифметика для int-кода (правильное
целочисленное деление), i32→f64 авто-приведение,
f64→i32 trunc, unary minus, `++/--`,
compound `+= -= *= /= %=`, `%`.

Управление: `if/else`, `while`, `for` (desugar), `foreach`,
`return`, `break`/`continue`. Вызовы: функции модуля по
индексу (включая рекурсию), builtin-хелперы выше.

Локали объявляются runs в порядке объявления (индексы
позиционные — группировка по типу ломает ссылки).
`__tmp` — скрытая externref-локаль для литералов
контейнеров.

Не поддерживается (падает на jit→js/eval): классы/методы
объектов (`a.method()` кроме push/pop/len/size),
исключения, closures/lambda, модули, `&&`/`||` с
некороткозамкнутыми операндами сложных типов,
вложенные `a.b.c = v` глубже одного уровня на set-стороне
(чтение цепочек `a.b[i]` работает).

i64/большие int через BigInt — не делаем: дорого и не нужно
в браузере (int покрывает |x| < 2^31).

## Сборка интерпретатора

`wasm/build.sh`: `OPT=1` по умолчанию (разработка — быстрый
прогон em++/wasm-opt), `OPT=2 bash wasm/build.sh` для
релизного бинаря. eval-скорость по оптимизациям:

| флаг | eval fib(25) |
|---|---|
| -O0 | ~2900 ms |
| -O1 | ~430 ms (6.5x) |
| -O2 | собирается медленно (wasm-opt на 1.3MB модуле),
       доп. выигрыш над -O1 умеренный |

## Авто-тиринг

После `nl_run` страница в фоне вызывает `nl_wasm_module`
и инстанцирует модуль — tintable-функции никогда не
попадают в eval при обычном использовании. `dispatch`:
wasm > jit→js (>3 вызовов) > eval. Интерпретатор —
fallback-движок для не-tintable кода (модули, классы,
исключения), а не первая стадия исполнения.

## Замеры (fib(25), ~242k рекурсивных вызовов)

| путь | время | разрыв |
|---|---|---|
| g++ -O2 (нативный nlang, честный noinline) | 0.160 ms | эталон |
| **nlang→wasm i32 (wasmjit)** | **0.228 ms** | 1.4× |
| nlang→wasm f64 | 0.256 ms | 1.6× |
| jit→js (V8 new Function) | ~0.68 ms | 4.2× |
| eval (wasm-интерпретатор -O1) | ~430 ms | ~2700× |
| eval (wasm-интерпретатор -O0) | ~2900 ms | ~18000× |

Честный референс: первый замер "g++ 0.08ms" был обманом —
компилятор поднял чистый вызов fib(25) из цикла (pure fn).
С volatile/noinline реальное число — 0.160 ms.

i32-режим: функции `int fn(int ...) -> int` эмитятся в i32
(i32.const/add/sub/mul/div_s + i32-сравнения) вместо f64.
Это +11% и правильная семантика целочисленного деления.
Режимы не смешиваются: i32-fn может звать только i32-fn.

Остаточные 1.4× до g++ — это call-overhead движка на
~242k прямых вызовах (instance/frame bookkeeping в V8),
не качество инструкций. На цикловой арифметике разрыва
практически нет: sums(50k итераций) ~0.1ms и там и там.

wasm-opt (binaryen 130 из msys2) на наших модулях зависает
и даёт не больше +10% — V8 сам оптимизирует wasm (Liftoff→
TurboFan). Для продакшена wasm-opt не обязателен.

## Canvas-приложение без DOM (boot.js)

`wasm/out/boot.js` — фиксированное «ядро ОС» (~100 строк,
пишется один раз): загрузчик + env-хелперы + canvas +
маршрутизация событий. Единственный JS в проекте;
прикладной код — только nlang → wasm.

UI идёт через `<canvas>` (модель Flutter-for-web): DOM —
пустой контейнер. nlang-API:

```nlang
canvas.rect(x, y, w, h, "#color")
canvas.text("стр", x, y, "#color")
canvas.clear(w, h)
canvas.line(x1, y1, x2, y2, "#color")
canvas.circle(x, y, r, "#color")
```

События: экспорты `on_click(x,y)`, `on_move(x,y)`,
`on_key(code)`, `on_start()` — ядро само подключает
слушатели если экспорты существуют.

Глобальные переменные верхнего уровня (`int`, `dbl`)
становятся mutable wasm-глобалами — состояние живёт
внутри wasm-модуля (`clicks += 1` в обработчике обновляет
глобал). Семантика flat-vars как в интерпретаторе:
`x = v` в функции пишет в существующий глобал,
не создаёт теневую локаль.

jit→js убран из автоматического пайплайна: пользовательский
код никогда не компилируется в JavaScript. `nl_fn_js`
остаётся только как отладочный API (посмотреть
человекочитаемый вывод функции).

## Связь с нативным jit.cpp

Та же философия: ленивая компиляция, tintable-подмножество,
escape-hatch в интерпретатор. Различие: нативный jit эмитит
машкод и зовётся внутри NObject::call; браузерный — текст JS и
wasm-байткод, зовётся снаружи через экспорты (граница JS/wasm —
тонкая только на стадии 3, у стадий 1-2 она на каждый вызов).
